# Conference rooms

## Behavior

Conference rooms provide one shared dialable number for several callers. The editor is a guided control surface rather than a generic resource form. It offers creation presets, numeric steppers, a capacity slider, switches with visible on/off state, field-associated corrections, a generated review summary, and validated advanced details. The room name is required and bounded to 1–80 characters. The separate **Accept calls** switch controls the resource's enabled state.

Suggested defaults and presets appear only while creating a room. Editing loads the saved name, enabled state, revision, and conference values without relabelling them as defaults. Loaded switch values must be JSON booleans; strings such as `"false"` are rejected instead of being treated as truthy. Saving an edit sends the loaded revision as `expectedRevision`, preserving optimistic-concurrency behavior.

The supported configuration contains exactly seven fields:

| Field | Bound or default | Native behavior |
| --- | --- | --- |
| Conference number | 2–12 digits; the editor suggests `700` | The number generated by the FreePBX Conferences module in `ext-meetme`. |
| Maximum participants | Required integer from 2 through 200; the editor suggests `20` | Passed as the FreePBX conference `users` limit. Asterisk's native unlimited default is deliberately not represented by this bounded editor. |
| Record conference | Off | FreePBX option `r`; recording starts with the first active participant and ends after the last leaves. |
| Announce join and leave | Off | FreePBX option `I`; callers record their names, and those recorded names are played on join and leave. |
| Start muted | Off | FreePBX option `m`. Option `s` is always included so the standard FreePBX user menu is available and `*1` toggles mute. |
| Music while empty | Off | FreePBX option `M`; requests the PBX default music class while a caller is alone or waiting. |
| Quiet mode | Off | FreePBX option `q`; suppresses entry, exit, and recorded-name announcements. |

Quiet mode and join/leave announcements cannot both be enabled. The protocol, module validator, compiler, and editor all reject that combination with a correction in plain language.

Room-level controls are shown separately from participant-level controls. The number, participant limit, and recording choice describe the shared room. Announcements, start-muted behavior, waiting music, and quiet mode describe what each joining user experiences.

Each correction is associated with its control. A refused save focuses the first invalid room name, enabled state, number, capacity, or participant-behavior control. Escape, backdrop close, and Cancel all intercept a dirty editor and require an explicit **Keep editing** or **Discard changes** decision; closing returns focus to the control that opened the editor.

## Local drafts and connection behavior

Disconnected saves use a versioned `v1` browser-storage envelope bounded to 100 resources and 256 KiB total. Each retained row is visibly labelled **Local draft · not sent**. Corrupt, unknown-version, malformed, or over-bound storage is rejected rather than partially loaded.

Connecting loads server records and local drafts as separate rows. It does not merge or send a draft automatically. The operator must open **Review and send draft**, review every field, and explicitly submit it. A successfully accepted submission removes that local copy; a failed submission keeps it for another review.

## Native FreePBX application

The typed `conference` request maps from the `conferences` resource kind through the normal immutable request snapshot and optimistic-revision path. The compiler produces a deterministic `conference-freepbx-bmo-v1` artifact containing only values consumed by the FreePBX 17 Conferences module plus explicit MaterialPBX ownership metadata.

The module requires the concrete `FreePBX::Conferences()` service and the `addConference`, `getAllConferences`, `updateConferenceSettingById`, and `deleteConference` methods. Missing module or API support fails closed before mutation. It deliberately uses `getAllConferences()` for SQL existence checks because the upstream `getConference()` method can return `false` after either a SQL or Asterisk Manager read failure, which is not proof that a room is absent. It does not write `confbridge.conf`, invent a profile-file API, or add a parallel dialplan. FreePBX owns `ext-meetme`, its dynamic bridge and user options, and its standard user menu.

New rooms are created with empty user and administrator PINs. This editor does not accept PINs, moderator roles, arbitrary dialplan, shell commands, recording paths, music-class text, or free-form Asterisk configuration.

## Ownership, updates, deletion, and rollback

Each compiled artifact has a deterministic ownership prefix derived from the MaterialPBX resource identifier. That prefix is placed at the beginning of the FreePBX conference description and retained inside the 50-byte database field without splitting UTF-8 text.

Before update or deletion, MaterialPBX requires both its compiled-artifact ownership record and exact matching SQL and Asterisk database state. The SQL comparison covers room number, ownership-marked description, options, participant limit, empty PINs, empty language/music/join-message settings, and the bounded timeout. The runtime comparison covers all eight consumed AstDB keys: language, user PIN, administrator PIN, options, music, users, join message, and timeout. A missing, externally changed, unreadable, incomplete, or non-owned state fails closed without mutation.

A new or changed room number must pass FreePBX's extension-range check and global extension-usage check before mutation. Existing source rooms also repeat the range-authorization check before update, move, or deletion. Room-number changes move dependent FreePBX destinations through `conferences_getdest()` and `framework_change_destination()`, with reverse migration in compensation. Deletion and number changes fail closed when Sangoma's separate REST conference integration is enabled or when its module status cannot be established, because that separate record has no reviewed reversible API here.

FreePBX Conferences calls update both the SQL row and Asterisk database state. Therefore a database rollback is not treated as sufficient. Create, update, room-number change, disable, delete, and compilation rollback use explicit BMO compensation. A partial change restores the complete prior SQL row and all eight AstDB values; a replacement room is removed when necessary. Compensation failure is reported separately instead of being hidden.

MaterialPBX serializes its own writers per conference number through private service-owned lock files inside the persistent root-owned `/var/lib/materialpbx/locks` directory, taking old and new room locks in deterministic order for a move. This prevents two MaterialPBX requests from interleaving and survives ordinary host reboots, but it is not a database reservation shared with FreePBX's own UI or another module. An external FreePBX writer can still race between the preflight and the upstream SQL insert or destination update. Until a shared transactional reservation exists and is proven on a live host, operators must not edit the same room concurrently through another FreePBX surface.

## Recording and media limits

Enabling recording places files in the PBX recording store. Retention, access, export, capacity, and applicable notice or consent policy remain operator responsibilities and are called out beside the switch.

Enabling waiting music requests the PBX default music class. Successful validation, compilation, or reload does not prove that media exists or is audible. Verify it with a real call.

## Result semantics and failure modes

- Validation failure does not send a mutation and explains the required correction.
- Missing FreePBX Conferences support fails before any native row changes.
- An occupied number, global extension conflict, missing ownership marker, SQL/AstDB drift, non-empty PIN, unavailable state read, unsafe Sangoma integration state, or unavailable private lock fails closed.
- `applied`, `reloaded`, and `runtimeVerification: pending` remain independent result fields. A stored or reloaded room is not described as live until a real call verifies it.
- A reload failure preserves the applied result and reports partial failure; it does not invent runtime success.

## Verification

Focused local checks cover protocol defaults and every bound, wrong types, unexpected fields, the quiet/announcement conflict, typed dispatch, deterministic compiler output, start-muted unmute-menu inclusion, UTF-8 description truncation, module/API registration, UI-helper presets and serialization, exact UI wiring registrations, client mutation/result mapping, bounded versioned local-draft persistence, SQL-versus-AstDB absence handling, full native-state comparison/restoration, extension-range and global-usage refusal, deterministic lock ordering, destination migration and compensation, Sangoma-integration refusal, create/update/room-change/delete compensation, non-owned deletion refusal, and unchanged-resource drift detection. The web production build also completed. The source-level UI contract is not built-artifact interaction evidence.

No real FreePBX 17 conference call, recording file, music playback, runtime participant cap, full reload, external-writer race, service-account lock-directory use, destination migration, or built-interface interaction was performed in this change. Runtime verification remains pending.

Conference-specific copy remains fixed English in this implementation. Complete English, Cantonese, and bilingual localization is an open incomplete feature and is not claimed by this work.
