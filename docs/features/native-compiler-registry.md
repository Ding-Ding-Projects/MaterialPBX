# Native compiler registry

The native compiler registry separates stored desired state from generated PBX output. It previews an exact bounded diff, records a snapshot identity, applies module-owned output in one database transaction, reloads FreePBX separately, and leaves runtime verification explicitly pending.

## Supported native output

Version 1 compiles only enabled ring groups with validated members, a 1–300 second ring time, and terminate failover. It stores a module-owned artifact and renders the context through FreePBX's `get_config` hook using fixed `NoOp`, `Dial`, and `Hangup` objects. It never writes core configuration files or native FreePBX module tables.

Extensions have a bounded `extension-get-config-v1` compiler that generates the module-owned internal context for a validated 2–12 digit numeric extension. IVRs compile 1–12 unique key choices using digits 0–9/`*`/`#` and allowlisted destination types with a 1–60 second timeout. Voicemail boxes compile validated numeric mailboxes, optional valid email notification settings, attachment choice, and 10–3600 second message limits. Time conditions compile 1–32 weekday/start/end windows against a real IANA timezone. Inbound routes compile validated DID patterns, optional Caller ID patterns, and allowlisted destination types into module-owned contexts. Outbound routes compile 1–128 valid dial patterns with 1–16 trunk identifiers; emergency routes must name exactly one trunk. Queues have bounded `queue-get-config-v1` support for enabled queues with one to 256 unique validated members, a supported Asterisk strategy (`ringall`, `leastrecent`, `fewestcalls`, `random`, or `rrmemory`), terminate failover, and a 1–3600 second timeout.

Trunks have a deliberately narrow `trunk-get-config-v1` compiler for credentialless PJSIP trunks using UDP, TCP, or TLS with a valid host/IP and port. The generation hook writes only fixed, field-validated endpoint/AOR/identify records to `/etc/asterisk/pjsip_materialpbx_custom.conf`. Registration and referenced credentials remain unsupported until reviewed provider-specific handling exists.

Conferences use a different native boundary. The deterministic `conference-freepbx-bmo-v1` artifact declares the FreePBX 17 Conferences BMO route, a 2–12 digit room, a required 2–200 participant limit, canonical option letters, and explicit MaterialPBX ownership metadata. The module calls `FreePBX::Conferences()` and requires `addConference`, `getAllConferences`, `updateConferenceSettingById`, and `deleteConference`. SQL existence is read separately from Asterisk database state so an upstream read failure can never be interpreted as an absent room. FreePBX then owns `ext-meetme`, dynamic ConfBridge options, and its standard `*1` mute-toggle menu. MaterialPBX does not write a custom conference profile file or parallel conference dialplan.

## Transactions and rollback

Before replacing a compiled artifact, the module locks the prior row and stores its compiler and artifact under a UUID snapshot. Artifact replacement and snapshot creation commit together. Rollback is single-use: it locks the snapshot, restores or removes the prior module-owned artifact, and marks the snapshot restored in one transaction. `POST /v1/resources/compiler/rollback` performs only that restore; FreePBX reload and runtime verification remain pending and are returned as such.

Conference transitions additionally verify the live FreePBX SQL row and all eight consumed Asterisk database values against the artifact's deterministic ownership state. BMO calls mutate both stores, so create, update, number change, disable, delete, and rollback use explicit compensating BMO operations. A conflicting, unreadable, incomplete, or externally edited room is never adopted. New numbers must pass FreePBX's range and global extension-usage checks, and existing source numbers repeat the range check. Room-number changes migrate dependent destinations through FreePBX's own destination functions and reverse that migration during compensation. The operation refuses deletion or moves when the Sangoma REST conference integration is enabled or its status is unavailable.

Private per-room file locks under the persistent root-owned `/var/lib/materialpbx/locks` directory serialize MaterialPBX writers, and moves acquire both numbers in sorted order. These locks are not shared by the FreePBX UI or other modules, so they do not close the external-writer gap between preflight and upstream mutation. Live-host proof, including a competing external writer and the FreePBX service account's access to the persistent lock directory, remains required.

Unsupported or disabled compilation still upserts the normalized desired record in its own transaction before returning `storedDesired=true`; compiled output remains untouched. Deleting a resource locks any compiled artifact, snapshots it, removes desired and compiled rows in one transaction, and returns a removal diff plus rollback identity. When no compiled artifact exists, deletion removes desired state but reports native compilation unsupported and does not trigger a reload.

Disabling a previously compiled ring group is a supported removal transition: desired state, snapshot, and compiled-artifact removal commit together, then FreePBX reloads while runtime verification remains pending. If no compiled artifact exists, disabled desired state is stored as an honest no-op with no reload. For any other unsupported edit with prior compiled output, the result explicitly says that output was retained and runtime may differ from desired state.

## Result semantics

Responses distinguish `storedDesired`, compilation status and diff, snapshot identity, `applied`, `reloaded`, `runtimeVerification: pending`, partial failure, and rollback outcome. `storedDesired` is `null` when the privileged helper fails before returning a request-bound result, because a transport failure cannot prove whether the desired-state transaction committed or rolled back. A compiler-unsupported result exits successfully at the bounded bridge but returns `applied=false`; the control plane does not reload FreePBX.

## Limitations and verification

FreePBX 17 loads BMO module classes from the `FreePBX\modules` namespace. Installation migrations use the platform's `FreePBX::Database()` handle, while console commands must accept zero-argument construction and obtain the BMO container through `FreePBX::create()`. The container image exposes the package-installed `/var/lib/asterisk/bin/fwconsole` through `/usr/local/bin/fwconsole` before first boot. `/etc/freepbx.conf` is deliberately not a Docker volume because Docker creates a directory for a missing file-path volume, preventing FreePBX from creating its configuration file.

Runtime evidence covers one bounded path. MaterialPBX module 0.1.0 installed and enabled on FreePBX 17, and the resources, compiled-artifact, and compiler-snapshot tables were created. A ring-group artifact compiled with snapshot records. Rolling back its single-use snapshot removed the artifact, restored the prior-null state, and marked that snapshot restored.

Full FreePBX reload is not yet proven. The exercised container came from an older interrupted first boot and did not contain the generated custom include files expected by its FreePBX configuration. A fresh clean image build and boot are required before reload can establish that generated output is included. No real call, cross-resource destination dispatch, disablement, deletion, or credentialless trunk call has been proven.

Generated extension, route, IVR, voicemail, queue, ring-group, time-condition, trunk, and conference output is module owned but does not yet prove end-to-end destination linkage across resource types. Generation records bounded contexts, patterns, schedules, or owned FreePBX module rows; actual destination dispatch needs live verification. Ring-group and queue membership assumes PJSIP endpoint identifiers match validated members; outbound trunk selection assumes identifiers match compiled trunk endpoints; trunk generation assumes credentialless direct-IP service. Conference configuration does not prove a real call, recording, music playback, capacity enforcement, or reload.
